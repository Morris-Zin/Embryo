# ADR 0003: Stock lock granularity and remaining serialization

**Status** — Accepted design for run `backend-2gb-proof-20261128`. Implementation and capacity acceptance depend on the gates below.

## Context

ADR 0002 retained transactional invoice numbering. At 100 sales/min, caching reduced weighted series hold from 662 to about 437 ms. In the baseline, 96% of sampled Item wait edges led directly or indirectly to a series holder. Independently committing the number reduced series hold to 3.4 ms, but the Item locks still lasted a weighted mean of 714 ms through commit. Two sales of the same SKU at different shops could therefore queue behind each other. The paired HTTP p95s (about 2.9 s baseline and 5.07 s experimental) do not establish a regression or an improvement. Another flag-off run reached 10.7 s on the shared host.

**Installed reference.** The KhitmeeERPNext perf bench reported ERPNext 16.60.0 and Frappe 16.60.2. The site SQL session reported MariaDB 11.8.10 and REPEATABLE READ. The following observations apply to the installed source.

- In `erpnext/stock/stock_ledger.py:161`, `make_sl_entries` checks for future entries, submits each SLE, resolves the Bin, reads reserved stock, reposts the current voucher and updates the Bin. This loop has no blanket Item mutex. The imported `update_bin_qty` is `stock.doctype.bin.bin.update_qty`. It reads Bin quantities, can read the latest pair SLE, then writes the Bin by name. The write takes an exclusive lock. An earlier ordinary read does not.
- `repost_current_voucher` invokes `update_entries_after` and `update_qty_in_future_sle`. Current and preceding voucher-ledger lookups use pair-scoped locking reads (`get_sle_against_current_voucher`, `get_previous_sle_of_current_voucher`). Other reads can use snapshots. The future UPDATE filters active SLEs by item and warehouse, handles creation order at equal posting time and can stop at a reconciliation. The controller's voucher-wide future check unions the applicable pairs. Its final MariaDB locking check bypasses the ordinary-read cache. Preserve both the repost decision and negative-quantity validation.
- Normal valuation uses the pair's ledger history. The Item/company valuation method selects the algorithm. Negative-stock permission can depend on Item/settings, and a missing usable rate can read Item valuation rate, standard rate or Item Price. Serial identity, batch/bundle valuation, linked voucher rates and a transfer's source-to-target value flow need separate treatment. The buying controller also calls `update_last_purchase_rate`. A warehouse-local quantity does not imply that every read and write is warehouse-local.
- `stock/doctype/bin/bin.py:on_doctype_update` declares `unique_item_warehouse`. Live `information_schema.statistics` confirmed NON_UNIQUE=0, sequence 1 item_code, sequence 2 warehouse. In `stock/utils.py:307`, `get_or_make_bin` looks up the pair. On a miss, `_create_bin` inserts under a savepoint and catches UniqueValidationError, rolls back to the savepoint and rereads. Uniqueness prevents two committed Bins. It does not refresh a prior RR snapshot, guarantee a visible winning row, or prevent a gap-lock deadlock.

## Decision

**Narrow exclusive ownership to the Bin for ordinary existing-stock sales. Reject a universal “lock Bins, then lock the Item on a miss” rule.** Pair exclusion through commit is at least as strong as the inspected native path for competing ordinary submissions on that pair, provided all relevant writers cooperate and the reader has the required visibility. For the first implementation, retain a **shared** Item lock for ordinary items. This allows two shops to sell one SKU concurrently, preserves exclusion against Item master writes, and lets conservative paths take an exclusive Item lock that ordinary sales actually respect. Keep the existing implementation selectable throughout qualification. Change only the custom app.

1. **Plan the whole voucher before acquisition.** Resolve canonical database identities and deduplicate every potential SLE coordinate, including packed components, both transfer legs, transit, returns and rejected or supplied material where applicable. Use identical ordering and identity normalization in all entry points. Treat preflight reads as hints. Classify known ordinary, untracked, existing stock as shared-Item/exclusive-Bin. Start conservatively with exclusive Items for purchase paths that may write Item, tracked stock, negative-stock or exceptional valuation paths and unclear dependencies. A voucher with unknown affected items/warehouses cannot use the cached absence proof. Preserve native posting order, especially the source valuation before its transfer receipt.
2. **Serialize first creation without inversion.** Preflight may predict a missing Bin. Mark that Item exclusive from the outset. Acquire all Item locks in canonical name order, using each Item's strongest required mode once. Then acquire existing Bins exclusively in canonical (item_code, warehouse) order irrespective of voucher row order or transfer direction. Use exact indexed point locking reads in order as the reference implementation. Batch only after demonstrating actual acquisition order and bounded lock footprint on the deployed engine. SQL output order alone proves neither. Hold all locks to the outer transaction boundary. For an expected miss with the Item already exclusive, retain its protection through native Bin creation if posting requires it. Do not eagerly create Bins for non-stock rows. Distinguish physically locked existing Bins from missing coordinates protected by the exclusive Item. Cache names only for rows actually found.
3. **Handle surprises by restarting at the boundary.** If an expected existing Bin is missing under a shared Item, abort the entire attempt, then replan with the affected Item exclusive. Never promote a shared lock in place or take an Item lock after a Bin lock. Use a bounded whole-request retry with jitter and the same idempotency key, only after confirmed rollback. On an ambiguous commit resolve the key before replay. For an enclosing Desk transaction surface a retryable failure and roll back the enclosing operation. No internal commit or savepoint retry of a stale snapshot. The unique key remains the last line of defense for a creator outside the protocol.
4. **Preserve F01's visibility rule.** For a counter voucher, finish advisory reads, reset a write-free preflight transaction as today, then take the full lock set before the *first consistent read* of the posting transaction. Capture the automatic posting timestamp after locks. Check the actual SQL sequence, including idempotency handling. A locking read after a wait sees current data but cannot advance an already established read view. A Bin existence query, master lookup or hook that opens that view early invalidates the absence proof. If freshness cannot be established, keep upstream future updates and disable visibility-dependent caches. Never roll back caller-owned work to enable a fast path. Even with a fresh view, skip only for an owned, proven-empty pair, exact timestamp/voucher and the existing one-skip-per-pair guards. Preserve native validation. Use the full path for tracked stock, applicable negative-stock settings, cancellation, landed cost and exceptions.
5. **Use the same protocol in Desk.** The existing before_submit hooks for Sales Invoice, Delivery Note, Stock Entry, Stock Reconciliation, Purchase Receipt and Purchase Invoice must use the same planner and acquire before the first SLE mutation. For a prelocked API call, verify final coordinates and lock modes are a subset of those held. On expansion, abort and replan the whole operation. Never append an out-of-order lock. Desk submissions can have an older view or prior locks and must not infer freshness from before_submit. Non-stock purchase invoices need no stock Bin solely because an item is listed. Preserve protection for actual Item writes. Clear transaction-local ownership at commit and rollback and invalidate it if locks cease to be owned.
6. **Bound the claim.** Ordered acquisition prevents a cycle solely among participating Item/Bin acquisitions. RR gap locks, native SLE index ranges, linked docs, series, GL, reservation rows, Desk writes before the hook and background writers can still deadlock. A nonparticipant that inserts an SLE before waiting on a Bin does not honor the absence protocol. **UNCERTAIN** whether every cancel, repost, reservation, stock adjustment, or customization affecting a candidate's proof participates early enough. Trace these writers and force interleavings. Keep the optimization off for scopes permitting an uncovered writer until participation or an equivalent database-enforced absence proof is demonstrated. Retaining exclusive Item locks on just the nonparticipant's nominal counterpart cannot solve this.

## Alternatives rejected

- **Unconditional Bin-only locking.** It loses the Item master exclusion and leaves an exclusive-Item fallback invisible to ordinary sales at another warehouse. A duplicate key addresses row identity alone. A Bin-first miss fallback also creates an explicit cycle with Item-first Desk posting.
- **Early unlock, split SLE/GL commits or asynchronous stock posting.** These expose a partial voucher or admit another writer between valuation and commit. Keep the voucher, stock, GL and idempotency outcome atomic.
- **Enable independent invoice numbering by default.** Keep `khitmee_independent_invoice_series` **off**. Live tests established that a failed voucher after reservation leaves an audited gap, voucher commit order can differ from number order, and delete-last or `revert_series_if_last` never reuses an audited number. These are observable changes to the oracle's numbering contract. If narrowing alone meets the target there is no performance case to ask the owner to accept them. If series contention still blocks acceptance, present isolated matched runs and obtain an explicit owner decision on the numbering contract, including the accounting review required by ADR 0002, before any rollout. Until then the experiment cannot qualify as exact parity.

## Consequences

A truly hot **same pair** still queues until commit. If every sale touches that pair and its hold remains 714 ms, its illustrative capacity is only 84 sales/min. At 80 and 100 sales/min that would consume 95% and 119% of one serialized resource before any transfers or receipts. Measure actual pair overlap and hold. With transactional numbering, 437 ms at 80 and 100 sales/min consumes about 58% and 73% of one series, before queue variability. Worker occupancy, SLE and GL locking, DB CPU and commit I/O remain even when those queues shrink.

At 100 and 125 **mixed vouchers**/min, 80% sales gives 80 and 100 sales/min. The measured 0.377 Python CPU-s per weighted sale *inside the hold alone* costs 0.503 and 0.628 cores, or 25% and 31% of two cores. The entire guest budget averages 1.20 and 0.96 CPU-s per mixed voucher. Subtracting measured sale CPU leaves 1.50 and 1.37 cores for all other work, including the remaining sale CPU, database, 20% non-sales and guest services. For a sales-only 100/125 probe the same lower bounds are 0.628/0.785 cores. The 714 ms lock hold is wall time and overlaps Python CPU. **UNCERTAIN** whether two cores suffice. Measure guest-wide CPU demand per completed class and runnable queue at steady throughput.

The weighted basket is 27.5 lines. At about 12 SQL calls per SLE line, sales alone imply roughly 440 and 550 calls/s at the mixed rates. A measured 2.6 s SLE phase on a 200-line sale already exceeds that class's entire 1.5 s latency budget. Moving other work outside locks cannot fix that service time. In order:

1. Move deterministic payload decoding, row normalization, pure conversions, ordering and construction of immutable child inputs before lock acquisition. This shortens holds but saves CPU only if it also removes repeated work.
2. Batch repeated metadata/schema lookups and prepare candidate master data outside the window. Revalidate mutable decisions under the same permissions and transaction visibility. Audit bundle, reservation and Item caches independently. Shared Item locks alone do not protect changes to Item Price, settings or child tables.
3. Profile 200-line native calls by SQL fingerprint and Python stack. Eliminate redundant reads using supported custom-app seams only where query results, hooks, precision, line order and visibility stay identical. Keep authoritative stock availability, prior/future SLE, rate calculation, transfers, Bin and GL writes inside the transaction. If native service time still exceeds budget, report failed capacity for that basket.

## Verification plan

1. On paired restored fixtures record installed versions/source fingerprints, index definition, posting-session isolation and flags. Run two-connection barrier tests for same SKU/different warehouses (both ordinary sales pass the Item stage concurrently), same pair (second waits and sees predecessor), simultaneous first receipt, absent Bin after preflight, master edit, purchase rate write, reverse-direction transfers and overlapping 200-line baskets. Exercise Desk against API for each hooked doctype. Inspect physical locks and deadlock reports, compare a committed winner and rolled-back winner, and verify a retry posts exactly once.
2. Force a later-dated SLE to commit while an earlier-dated sale waits, with and without an already-open read view. Cover equal timestamps, repeated lines, returns, cancellation, reconciliation, backdating, cross-warehouse transfers, tracked/batch and negative-stock cases, packed and rejected stock, background repost and lost confirmation. Compare native outcomes against an oracle replay with the same effective dependency order, including failures, per-line SLE quantities/rates/value/queue, Bins, Item fields, linked rows, GL and numbering. Run the required live gate `python tools/perf_parity.py --require-db`. Offline fast-check is supplementary.
3. Use a dedicated 2-vCPU/2-GiB guest and reserved, otherwise idle host CPU/storage. Run load generation elsewhere. Keep oracle and unrelated stacks off the measurement host during timing, without disrupting live systems. Pin versions, worker counts, fixture restore, warm-up, cache state, seeds, arrival schedule and hot-pair distribution. Record CPU steal/throttling, pressure, swap, I/O, restarts and OOMs. Mark infrastructure-contaminated runs and repeat the matched pair, retaining the originals.
4. Compare baseline, narrowing alone and, diagnostically, independent series alone/both with identical traces and randomized balanced order. For acceptance use **five independent full-hour repeats per rate per qualifying configuration**. Schedule 6,000 and 7,500 open-loop vouchers with the stated 80% sales and 75/20/5 sales basket mix. Fix and publish the remaining transfer/receipt/invoice mix. Record scheduled-to-confirmation as well as HTTP latency, arrival lag, backlog and drain, so worker saturation cannot hide behind a delayed load generator.
5. Report each run's cashier p95 overall and separately for 10, 50 and 200 lines, sample sizes, then median, IQR and min–max of the five run-level p95s. Do not pool repeats or average percentiles. Publish per-class CPU and phase wall time, actual series/Item/Bin holds versus waits, lock graphs, retry/error counts and resource headroom. Require every qualifying repeat at both rates to meet the 1.5 s per-class cashier p95, sustain scheduled demand with no accumulating backlog, and have zero drops, duplicates, unresolved outcomes, OOMs or oracle differences. A fast median with a failing repeat leaves capacity unproven.
