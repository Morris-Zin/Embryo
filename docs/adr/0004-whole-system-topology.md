# ADR 0004: Whole-system topology and 2 vCPU emulation

Accepted design for run `backend-2gb-proof-20261128`, 2026-11-28. Capacity remains unproven.

## Context

The two completed base PR #17 smoke runs used the same short seasonal profile, including overload and recovery. Neither included this run's cashier or report improvements. The source records are `perf-suite/results/qualify-gunicorn-2x1-smoke-20261128T122152Z/` and `qualify-gunicorn-1x12-smoke-20261128T123214Z/` under the results directory (scorecard, final result, container stats and k6 log).

| Smoke observation | ADR 2 workers × 1 thread | Incumbent 1 worker × 12 threads |
|---|---:|---:|
| Final verdict | NO-GO | NO-GO |
| Running-service memory limits, MiB | 1,568 | 2,000 (outside prior budget) |
| Vouchers started / recorded completed, of 737–756 scheduled | 202 / 141 | 364 / 198 |
| k6 dropped iterations across scenarios | 693 | 642 |
| Baseline sale / search p95 on returned samples, seconds | 41.7 / 35.4 | 43.4 / 25.0 |
| Backend CPU consumed / throttled, seconds | 148 / 15 | 224 / 115 |
| Redis cache / background worker throttled, seconds | 202 / 47 | 10 / 165 |

Both runs lost observations and produced no successful warm-summary or detail sample or verified export. Detail returned 403 and enqueue returned 500 as well as timeouts. Neither more VUs nor faster SQL repairs an authorization or enqueue failure. In roughly six minutes the ADR backend averaged about 0.4 cores. Cache Redis consumed about seven CPU-seconds at its 0.02-core cap. Its throttle counter measures cgroup activity and cannot assign 202 seconds of latency to any request. No OOM was recorded. The ADR DB used about 482 MiB at its highest sampled current usage and recorded a 503 MiB cgroup peak under a 512 MiB limit. CPU quotas, memory limits, concurrency and completed populations all varied between runs.

## Decision

**Qualify on an exclusive Linux guest configured with two online vCPUs and 2,048 MiB total assigned RAM, swap disabled, with the kernel, daemon, caches and all application services inside.** Run k6 and the stock oracle outside. Use a single cgroup-v2 service parent. On a larger WSL host emulate the application boundary with a systemd slice on the Docker daemon's Linux host, Compose `cgroup_parent` for every service, two exclusive logical CPUs in `cpuset.cpus.effective`, parent `cpu.max=200000 100000`, `memory.max=2147483648` and `memory.swap.max=0`. Children use unlimited CPU quota and relative weights. Confirm ancestor limits, actual membership and effective values from host PIDs, including RQ children and replacement processes. A quota alone permits bursts across more than two schedulable CPUs. [Linux cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

The larger-host slice is a diagnostic replica. Its parent memory charge omits part of the OS and daemon. A dedicated WSL VM can qualify only with the same verified guest envelope, exclusive workload, representative storage and host CPU availability as the VPS. Record hypervisor settings and guest-visible resources. An unrestricted shared Docker Desktop VM or a passing sum-of-container-limits check cannot certify the guest. Replace the current supervisor's resource-proof predicate before accepting any run under the new model. Preserve lease, foreign-load and before/after restart checks.

**Start with two Gunicorn pools and one background worker.** These proposed child memory ceilings include masters, threads and forked children. CPU weights are effective sibling `cpu.weight` values to verify after deployment. A runnable service can borrow idle cycles.

| Service | MiB | CPU weight | Initial configuration |
|---|---:|---:|---|
| MariaDB | 544 | 300 | 320 MiB buffer pool, 32 connections, retain durable commits |
| Cashier | 416 | 300 | One preloaded gthread worker, three threads for short I/O overlap |
| Manager, login and general Desk | 224 | 100 | One preloaded sync worker, one in-flight application request |
| RQ worker and work horse | 256 | 50 | One job at a time across served queues |
| Scheduler | 96 | 30 | One scheduler |
| Redis cache | 64 | 150 | 32 MiB maxmemory, allkeys-lru for disposable cached data |
| Redis queue | 32 | 120 | 16 MiB maxmemory, noeviction, monitor failed writes and job retention |
| Websocket | 72 | 40 | One process |
| nginx | 24 | 100 | Bounded buffers, direct static serving |
| **Running services** | **1,728** | | |
| **Guest OS, daemon and reserve** | **320** | | **2,048 MiB total** |

This fits on paper. The reserve is 160 MiB smaller than ADR 0002's trial allowance. The split introduces a second master and separate imported Frappe state. Verify peak under simultaneous export, large sale, login and worker recycling. Include socket buffers, filesystem cache, DB temporary tables and idle connections. Stage one-shot configuration outside the measured window and account for startup inside the guest limit. A memory event, sustained reclaim or insufficient OS reserve triggers resizing and remeasurement. Measure Redis fragmentation, misses, evictions and write errors. Confirm cache eviction is safe for the installed key uses. Keep queued jobs and durable coordination state outside the evictable cache.

nginx routes exact cashier submit and search methods to the cashier socket, and report, export enqueue/status, login and Desk boot to the general socket. Serve public versioned assets directly and preserve authentication for private files. Inventory the entire confirmation path: sales and transfers use custom submit methods, search uses `khitmee_ops.api.search.search_items`, purchases use `frappe.desk.form.save.savedocs`, and recovery can read documents. Use a dedicated counter ingress for these shared method/resource paths with a narrow method/path allowlist and normal site, session, CSRF and document permission checks. General Desk traffic stays on its own ingress. Bind both to the same site, and verify site selection and cookie scope with real actors. Never use client-supplied role headers as authority. Exercise normal production URLs through nginx in k6.

Start admission at two concurrent voucher operations and one search per cashier worker across clients, using shared nginx zones for separate classes, one general application slot and a small measured login burst allowance. Count all admission failures. Tune the general slot/queue using the manager cadence and boot evidence. Buffer request bodies before forwarding, bound backlog and timeouts, disable automatic proxy retries on writes and rate-limit login separately. Under overload return a prompt, accounted-for 429/503 and resolve ambiguous writes by the existing idempotency path. For target-rate runs every scheduled transaction must succeed. Isolation removes shared HTTP slots. CPU, DB and Redis remain shared. A long Python phase can delay search even in its reserved slot. Threads overlap socket/DB waits but contend on the interpreter GIL for Python CPU and increase per-request Frappe state, DB connections and lock waiters. Compare two cashier processes only if measured CPU/GIL delay warrants the memory cost. Verify concurrent request-local user, site, transaction and teardown isolation.

Run the full-year export as a permission-checked RQ job with one active export, bounded pending work and a small enqueue/status response. Bind job and download to the requester and authorized scope. Page through a deterministic, consistent report view with bounded fetch sizes, stream CSV to a temporary file, then publish on success. Preserve oracle ordering, values and report snapshot semantics during concurrent postings. Include worker plus child peak, DB snapshot lifetime, disk writes, completion time, failures and retries. Long export occupancy can delay other background jobs. Track oldest job age and require drain.

**Reuse authenticated sessions on the normal client lifecycle.** The scenario already caches a session per VU/actor and sets `noCookiesReset`. Login posts credentials and fetches `/app` for CSRF when needed. The ADR log contains 391 login begins and 196 ends, all 196 reporting Desk boot. Incumbent has 244 begins and 185 ends. The discovery VU alone recorded 599 ms login plus 2,457 ms boot on ADR. Startup/churn is material traffic. Its share of steady CPU and latency is **UNCERTAIN**. Failed initialization may be retried by a later iteration. Keep one real SID and CSRF token per active client/actor, honor expiry and revoke/logout, and never share a privileged prebuilt session. Measure realistic shift-start, expiry and steady-state logins separately. A staggered authenticated warm-up may precede the steady hour if published separately. Keep first-use and reauthentication traffic visible and compare a cold-start smoke. Production clients reuse their own valid sessions.

## Alternatives rejected

Fixed child CPU quotas strand idle budget and periodically stall a dependency on the request path. A shared 1×12 pool allows one login or export burst to occupy cashier slots. A single shared sync pool similarly lets slow reports block intake. A process per route or a dedicated export web worker spends the limited memory on additional initialized Frappe interpreters. Reconsider finer isolation only with measured peaks and queue attribution. Keep ERPNext/Frappe unmodified and transactional numbering enabled as in ADRs 0002–0003.

## Consequences

At 100/125 mixed vouchers per minute the entire guest has 1.20/0.96 CPU-seconds per voucher including all concurrent reads and background work. At 80% sales, 0.377 Python CPU-seconds inside the series hold alone uses 0.503/0.628 cores. That leaves 1.497/1.372 cores for other sale phases, non-sales, DB, Redis, reports, export and OS. The 437 ms weighted wall hold uses 58%/73% of one series before variability. Wall and CPU overlap. If every sale touched one pair held for 714 ms, that pair alone would saturate at about 84 sales/min. Measure actual overlap. The 2.6 s isolated 200-line SLE phase exceeds the whole 1.5 s class target before queueing, with roughly 12–13 calls per line. **100/min throughput is plausible but UNCERTAIN. The measured large-basket path cannot support a credible latency claim without a faster parity-preserving service path.** At 125/min both CPU and serialization margins shrink. The smoke confirms failure of those profiles and gives no saturated two-core capacity estimate.

## Verification plan

1. **Make one request of each type succeed at idle.** Pin commits, fixture, image digests, profiles and actor grants. Trace all URLs and actual upstreams through purchase confirmation and export download. Resolve detail 403 and export 500 using role-correct requests and tracebacks. Verify denials for unauthorized actors, correct first page and full-year CSV against stock. Fix duplicate start IDs and incomplete accounting before using throughput denominators.
2. **Instrument before changing topology.** Join generated request IDs across k6, nginx, Gunicorn, custom-app and DB observations. Record scheduled, iteration-entry, actor-ready, request-send and confirmation times, including login attempts, bootstrap and network simulation. At nginx log request, upstream connect, header and response times, statuses and pool. Use `$upstream_queue_time` only on a build supporting the upstream queue feature. Request time minus upstream response includes client transfer, buffering and other overhead. Successful connect can precede worker availability. Timestamp proxy dispatch, earliest WSGI entry, application completion and response end on calibrated clocks, compare with socket backlog and busy threads, and label the dispatch-to-entry interval as an estimate including transport. Sample app wall and thread CPU for auth/site initialization, handler, SQL, locks, serialization and commit without changing core. Preserve timeout and rejection traces. [nginx upstream timing variables](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#variables)
3. **Measure dependencies concurrently.** Sample per-instance Redis ping RTT from the app network, command latency/slowlog, hits, evictions, queue depth and command errors. Correlate DB connection IDs with series/Item/Bin/SLE waiter-blocker edges, lock acquisition and hold-to-commit, query counts, SQL fingerprints, commit I/O and connection occupancy. Capture parent/child CPU deltas and throttle periods, CPU/memory/I/O pressure, guest runnable/steal time, memory current/peak/events, swap and restarts over identical intervals. Avoid summing waiter duration as owner CPU. Quantify tracing overhead with a matched uninstrumented run.
4. **Change one factor per matched smoke.** Restore the same seed, fix VU capacity and schedule, run the base 2×1 first with hard caps then shared CPU, holding memory and topology fixed. Next isolate ingress/pools, then compare session arrival patterns. Apply cashier and report changes independently before combining. Record orchestrator overrides, effective Gunicorn class, weights and limits. Pair repeats in balanced order. Compare cold versus warm, cashier-only versus mixed with export, and same-pair versus distributed stock. Measure isolated 10/50/200-line CPU and wall by phase on the candidate. If low-load 200-line p95 misses, profile native SLE calls and test parity-preserving elimination of redundant work before scaling concurrency.
5. **Settle capacity at offered load.** Sweep through 80, 100 and 125 mixed/min with the approved 80% sales and 75/20/5 sales basket mix. Reconcile arrivals to unique committed outcomes. Measure guest CPU-seconds per completed class on single-class probes and total CPU-seconds per scheduled voucher during stable mixed throughput including searches, manager cadence and export. Report backlog slope, saturation and drain. Then follow ADR 0003: five independent restored full hours at each of 100 and 125 (6,000 and 7,500 scheduled), off-guest load generation, exact mix and timestamps, no accumulating backlog, drops, target-rate rejections, duplicates, unresolved outcomes, restarts or OOMs. Publish each run and class sample count and p95, including scheduled-to-confirmation and submit-to-confirmation. Require cashier <1.5 s in each basket class, search <300 ms, both warm summaries <500 ms, first detail page <2 s, and completed verified full-year export in each run. Preserve the seasonal overload/recovery checks separately from the steady hours. Run paired stock-oracle checks for numbering, voucher rows, SLE, GL, Bins, reports, retries and CSV under the same effective posting order, plus `python tools/perf_parity.py --require-db`. A short smoke, offline gate or subset percentile cannot qualify either rate.
